# Software Design and Engineering Enhancement Narrative

## Artifact Description

The artifact selected for this enhancement is a Python-based text adventure game that I originally created during an earlier term of my Computer Science program in IT 140. The game is inspired by *The Legend of Zelda* and places the player in the role of Link. The player begins in Kokiri Forest, travels through connected locations, collects six required items, and eventually faces Ganon at the top of Hyrule Castle. The original version included room navigation, an inventory system, item collection, win and loss conditions, an exit option, and a replay feature. I selected this project because it was one of my earlier programming assignments and provides a clear way to demonstrate how my approach to software design has developed since it was first created.

## Justification and Improvements

I included this artifact in my ePortfolio because it connects directly to my interest in game development while also providing a practical example of software that could be improved through stronger design choices. The original game worked, but much of its state was stored in global variables, and the main movement function handled several responsibilities at once. Input was case-sensitive, restarting the game relied on calling the main function again, and Ganon was stored in the same field used for collectible items. These choices made the project harder to maintain, test, and expand.

The enhanced version remains in one Python file, but the internal structure has been reorganized around a `Player` class and a `Game` class. The `Player` class now owns the current location and inventory, while the `Game` class manages the map, commands, room events, movement, item pickup, and game state. I separated these responsibilities into focused methods so that each part of the program has a clearer purpose. Commands are now normalized, allowing the player to enter different capitalization and extra spaces without being rejected. The game also accepts shorter commands such as `north` and `take Hammer` while continuing to support the original `go north` and `pick up Hammer` formats.

The restart system was redesigned to use an outer replay loop instead of recursively calling `main`. This creates a fresh game object for each session and prevents nested game loops from building up after repeated restarts. Ganon is now represented as a dedicated encounter rather than as a collectible item, and the Cucco Easter egg in the Kitchen was preserved as a separate room event. I also added clearer feedback for invalid directions, missing item names, unavailable items, and yes-or-no prompts. Type hints, constants, docstrings, and a standard Python entry point were added to make the file easier to understand and maintain.

## Course Outcome Progress

The completed work made solid progress toward the outcomes identified during the capstone planning process. Professional communication is supported through clearer naming, documentation, and a structure that another developer can follow more easily. The refactor also required evaluating design trade-offs. I considered splitting the project into several files, but one organized file was a better fit for the size of the artifact and avoided adding unnecessary complexity. At the same time, using classes and focused methods gave the game enough structure to support later improvements.

Object-oriented design, state management, input normalization, and separation of concerns were applied to turn the original assignment into a more maintainable program. The work also supports a security mindset on a small scale because user input is no longer assumed to be perfectly formatted. Unexpected commands and responses are handled in a controlled way rather than being allowed to disrupt the flow of the game.

## Reflection on the Enhancement Process

The most important lesson from this refactor was that improving software design does not always require changing what the user sees. Much of the original gameplay remains familiar, but the program is easier to reason about because the state and behavior are organized more carefully. Moving the inventory and current room into a `Player` object made it clearer which data belongs to the player. Placing the game loop and command processing inside the `Game` class also reduced the need for global variables and made the flow of the program easier to trace.

One challenge was finding the right balance between improving the architecture and overengineering a small text-based game. Breaking the project into many separate files would have created more structure, but it would not necessarily have added value for an artifact of this size. Keeping one file while using classes, focused methods, and reusable constants provided a practical middle ground. Another challenge was preserving the original story and gameplay while changing the internal design. The Zelda locations, six required items, final encounter, and Cucco Easter egg all remain, but they are now represented in a way that is more consistent with their roles in the game.

This enhancement showed me how much easier future changes become when responsibilities are separated early. The revised structure supports additional testing, new commands, more room events, and the breadth-first search hint system added in the algorithms and data structures enhancement. The artifact now better reflects my current software development skills while still preserving the original project that marked an earlier stage of my growth in the Computer Science program.
