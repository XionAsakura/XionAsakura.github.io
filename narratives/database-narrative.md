# Database Enhancement Narrative

## Artifact Description

The artifact I selected for this enhancement is Travlr Getaways, a full-stack travel application I created in CS 465 during the spring of 2026. It includes an Express and Handlebars website for customers, an Angular administration application, a REST API, and a MongoDB database managed with Mongoose. Each trip record includes a code, name, length, start date, resort, per-person price, image, and description. Customers can browse the available trips, while an authenticated administrator can add, edit, or delete records. I chose this project for the database category because it shows how data moves through the entire application, starting with the Angular form, passing through the API and Mongoose model, and ending in MongoDB before being returned to the user interface.

## Justification and Improvements

When I reviewed the original project, the basic create, read, update, and delete features worked, but the database still allowed several problems. The schema required values, yet it did not stop duplicate trip codes, trim values that only looked filled in, or place realistic limits on formats and ranges. Trip codes were used as identifiers even though MongoDB did not enforce their uniqueness. The per-person price was also stored as a string even though the Angular side expected a number. That mismatch created extra cleanup work and made the data less consistent than it should have been.

For the enhancement, I tightened the Mongoose schema so trip codes are trimmed, converted to uppercase, checked against an approved format, and protected by a unique index. The `perPerson` field is now stored as a number with minimum and maximum limits instead of formatted text. I added trimming and length rules for names, resorts, descriptions, trip lengths, and image names, along with a validator that blocks unsafe relative image paths. Timestamps now record when a trip is created or updated. I also added a text index for searchable fields and a combined start-date and price index to support the sorting and filtering features used by the application. A migration script was included so older records can be cleaned up before the new indexes are synchronized.

I also cleaned up the controller behavior so the API responds more consistently. An empty trip collection now returns a 200 response with an empty array instead of being handled like a missing resource. Creating a trip returns 201, updating one returns 200, deleting one returns 204 with no response body, and a code that does not exist returns 404. Updates use `runValidators` so the schema rules still apply after a record has already been created. Duplicate trip codes return 409, invalid data returns 400, and unexpected failures return a controlled 500 message without sending raw Mongoose or connection information to the user. Similar changes were made to authentication by normalizing email addresses, returning a clear message for duplicate registrations, and showing failed-login feedback in the Angular interface.

Search and filtering were added in a controlled way instead of allowing requests to send any database field they choose. The API supports text search, exact resort filtering, price and date ranges, sorting, ordering, and pagination. Sort fields are checked against an allowlist, page sizes are limited, and invalid ranges are rejected before a query reaches MongoDB. The Angular administration page now includes search, resort, price, and sorting controls that use those API options. Form validation was strengthened as well. During an update, the original trip code stays in the request URL while the edited trip is sent in the body, which allows the code to be changed without losing the record being updated. API, database, JWT, and CORS settings were moved to environment variables, public image paths were corrected, and clean routes were added for the Rooms, Meals, News, About, and Contact pages.

## Course Outcome Progress

The work matches the course outcome plan created during the capstone planning process. The database outcome is shown through the improved Mongoose schema, indexing, migration process, safe query construction, CRUD behavior, and the connection between MongoDB and the Angular administration application. It also supports the software engineering outcome because the enhancement could not be limited to one file. The models, controllers, routes, services, forms, configuration, and tests all had to stay consistent with one another for the application to work correctly.

Security was made part of the enhancement instead of being treated as a separate feature. Server-side validation remains the final check on submitted data, query options are restricted, unsafe image paths are rejected, JWT protection stays on routes that change data, and CORS uses an origin allowlist. Authentication and database errors now return controlled messages instead of exposing internal details. The work also required evaluating trade-offs. A unique index improves reliability, but it can reveal duplicate records that were previously accepted, so the migration process checks existing data first. Text and range indexes can improve read performance, but they also add storage and write overhead. I limited the indexes to fields connected to features the application actually uses.

## Reflection on the Enhancement Process

Changing `perPerson` from a string to a number made the connection between each layer of the application easier to see. The Mongoose schema needed to change, the controller no longer needed to remove currency symbols, the Angular model already expected a number, the form needed a numeric input, and existing MongoDB records needed a conversion path. Fixing the type at the database level removed repeated cleanup work from other parts of the project. It also reinforced that a small inconsistency in stored data can spread through the API and user interface when it is not corrected at the source.

The trip code update process brought up a different issue because the code also acts as the record identifier. If the request URL used the newly edited code, the API would try to find the trip under that value before the update had taken place. Keeping the original code separately and sending the edited record in the request body allowed the code to change without breaking the lookup. Authentication testing exposed another problem when a duplicate registration returned the full MongoDB duplicate-key error. I changed that behavior so the server can log the internal issue while the user receives a controlled 409 response. The login page was also changed to subscribe directly to the authentication request, which made failed credentials appear immediately instead of making the page look unresponsive.

I did not stop testing once the files passed a syntax check. The final backend suite includes 25 automated tests covering authentication, public routes, model validation, query safety, CRUD response codes, and controlled errors. All 25 tests passed, along with the JavaScript syntax check. I also tested the application locally by seeding MongoDB, running both the Express and Angular applications, opening the public pages and trip API, and registering and signing in with a new administrator account. Working through both automated and live testing helped me see how the database rules, API responses, frontend behavior, authentication, and error handling depend on one another in a full-stack application.
