# Algorithms and Data Structures Enhancement Narrative

## Artifact Description

The artifact used for this enhancement is the same Zelda-inspired Python text adventure game that I originally created in IT 140 and later refactored for the software design and engineering enhancement. The player controls Link while traveling between locations such as Kokiri Forest, Lake Hylia, Gerudo Valley, and Hyrule Castle. Six items must be collected before the final encounter with Ganon. By the end of the software design enhancement, the project already used `Player` and `Game` classes, normalized commands, focused methods, and a controlled replay loop. That version gave me a stronger base for adding algorithmic behavior without losing the story, locations, Cucco Easter egg, or other parts of the original game.

## Justification and Improvements

I kept this artifact in the ePortfolio because its room system naturally connects to algorithms and data structures. Each room can be viewed as a node in a graph, while the directions between rooms act as labeled edges. The original program used that structure only for direct movement, so the player could travel from one room to the next but the game could not examine the map as a whole. Adding a useful search feature allowed me to build on the existing design while showing how a graph algorithm can solve an actual gameplay problem.

The main addition is a hint command that uses breadth-first search to locate a shortest route. When Link is still missing required items, the search checks the room graph for the closest room that contains one of them. If the item is already in the current room, the player is told to pick it up. After all six items have been collected, the same search directs Link toward Ganon. The hint only gives the next direction and the remaining number of rooms rather than revealing the entire route, which keeps exploration as part of the game. A `deque` manages the search queue, a set prevents rooms from being visited more than once, and predecessor and direction dictionaries reconstruct the shortest path after a target is found. Because each reachable room and connection is processed no more than once, the search runs in O(V + E) time.

Inventory storage was changed from a list to a set because the game needs unique items and frequent membership comparisons more than it needs insertion order. A fixed item order is still used when the inventory is displayed, so the player sees consistent output while the program benefits from set operations. I also added a fixed direction order to make search results predictable whenever two goals are the same distance away. World validation now checks that every directional connection points to a real room, all required items appear exactly once, the starting and final rooms exist, Ganon remains in the final room, and every room can be reached from Kokiri Forest. These checks make future map changes safer because a broken connection or missing item is identified when the game begins instead of appearing later as confusing gameplay behavior.

## Course Outcome Progress

The strongest connection is to the course outcome focused on designing and evaluating computing solutions with algorithmic principles. Breadth-first search was selected because every move between rooms has the same cost, which makes BFS a practical way to find a shortest route without the extra complexity of a weighted-path algorithm. The search also required decisions about target selection and player experience. Guiding Link toward the nearest missing item is more useful than searching for one fixed item, while returning only the first move provides help without turning the command into a complete walkthrough.

The completed work also supports the outcomes related to professional communication and well-founded computing practices. Method names, docstrings, type hints, documentation, and the accompanying tests explain how the graph and search behavior fit into the game. Defensive validation contributes to the security-minded outcome by rejecting malformed world data and safely handling searches that cannot reach a target. The finished feature provides stronger evidence than the original proposal because the algorithm is connected to tested gameplay behavior rather than remaining only in pseudocode.

## Reflection on the Enhancement Process

Building the search feature changed the way I looked at the existing room dictionary. It had always represented connected locations, but treating it deliberately as a graph made it possible to use the same data for more than movement. The software design work from the previous enhancement helped here because the map, player state, and command processing were already separated well enough to add the hint system without rewriting the entire game. That progression made the value of planning for future changes much easier to see.

The most careful decision involved what the hint should reveal. Returning a full path would have been easier to demonstrate, but it would also remove much of the exploration that makes the game work. Providing one direction and a distance created a better balance between algorithmic usefulness and player choice. Equal-distance targets also needed a predictable result, which led to the fixed north, east, south, and west traversal order.

Automated testing helped confirm that the changes worked beyond a single playthrough. The tests cover valid and invalid world graphs, shortest paths, unreachable targets, equal-distance behavior, current-room hints, final-battle hints, and duplicate prevention in the inventory set. I also completed the full collection route and defeated Ganon to confirm that the new algorithm did not interfere with the story or game loop. All 14 automated tests passed.
