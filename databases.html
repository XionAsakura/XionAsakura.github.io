Enhancement Three

Databases

For the database category, I enhanced Travlr Getaways, a full-stack application created in CS 465. The project uses Express, Handlebars, Angular, a REST API, MongoDB, and Mongoose. The enhancement focused on stronger data integrity, safer API behavior, filtering, authentication handling, and testing.

Artifact Overview

Travlr Getaways includes a customer-facing site for browsing trips and an Angular administration application for managing trip records. Each trip includes a code, name, length, start date, resort, per-person price, image, and description. Authenticated administrators can create, edit, and delete records through the API.

Problems Identified in the Original

Data Consistency

Trip codes were treated as identifiers without database-enforced uniqueness. Some strings could contain weak or inconsistent values, and perPerson was stored as text even though the Angular side expected a number.

API Behavior

CRUD responses and error handling were not as consistent or controlled as they could be. Update validation, duplicate handling, missing records, and internal database errors needed clearer behavior.

Query & Security Controls

The application needed safer filtering, controlled sort fields, stronger validation, environment-based configuration, restricted CORS behavior, and cleaner authentication errors.

Database and Schema Improvements

Before

  • Trip codes not protected by a unique index
  • Price stored as a string
  • Limited format and length validation
  • No timestamps for created or updated records
  • Limited query-focused indexing

After

  • Trip codes trimmed, uppercased, format-checked, and unique
  • perPerson stored as a number with range limits
  • Length, trimming, and safe image-path validators added
  • Creation and update timestamps recorded
  • Text and compound indexes added for application-supported queries

API and Application Improvements

The enhanced controllers use more consistent HTTP behavior: successful creation returns 201, updates return 200, deletes return 204, missing records return 404, duplicate trip codes return 409, invalid data returns 400, and unexpected failures return a controlled 500 response without exposing raw Mongoose or connection details.

The list endpoint now supports controlled text search, exact resort filtering, price and date ranges, sorting, ordering, and pagination. Sort fields are restricted to an allowlist, page sizes are limited, and invalid ranges are rejected before the query reaches MongoDB. The Angular administration page uses these API options through search, resort, price, and sorting controls.

Authentication handling was improved by normalizing email addresses, returning a clear duplicate-registration response, and displaying failed-login feedback directly in the Angular interface. Environment variables are used for database, JWT, API, and CORS configuration, and public routes and image paths were corrected.

Security Mindset

Security was treated as part of the data design. Server-side validation remains the final check on submitted data, unsafe image paths are rejected, query options are restricted, JWT protection remains on operations that change data, CORS uses an origin allowlist, and database or authentication failures return controlled messages instead of exposing internal details.

Testing

The final backend suite includes 25 automated tests covering authentication, public routes, model validation, query safety, CRUD response codes, and controlled errors. All 25 tests passed, along with the JavaScript syntax check. The application was also tested locally by seeding MongoDB, running the Express and Angular applications, opening public pages and the trip API, and registering and signing in with a new administrator account.

Reflection

Changing the price from a string to a number demonstrated how one database decision can affect every layer of a full-stack application. The schema, controller, Angular model, form, and existing MongoDB data all needed to remain consistent. Fixing the data type at the source removed repeated cleanup work elsewhere.

The trip-code update process also required careful reasoning because the code acts as the record identifier. Keeping the original code in the request URL while sending the edited record in the request body allowed the identifier itself to change without breaking the lookup. Authentication testing exposed a raw MongoDB duplicate-key error, which was then replaced with a controlled response for the user.
