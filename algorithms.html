Enhancement Two

Algorithms & Data Structures

This enhancement builds on the software design refactor of the IT 140 Zelda-inspired text adventure. I treated the room map as a graph and added a breadth-first search hint system, graph validation, set-based inventory storage, deterministic traversal, and automated tests.

Why This Artifact Fits the Category

Each room functions as a node in a graph and each direction between rooms acts as an edge. The original game used that structure only for direct movement. It could move from one room to another, but it could not examine the map as a whole, find a shortest route, identify the nearest missing item, or validate the graph before play began.

Breadth-First Search Hint System

Target Selection

When the player is missing required items, the search targets rooms containing those missing items. After all six items are collected, the target changes to the final encounter with Ganon.

Shortest-Path Search

A deque acts as the queue, a visited set prevents repeated processing, and predecessor plus direction dictionaries reconstruct the route. Because the graph is unweighted, BFS is a practical shortest-path choice.

Player Experience

The hint returns only the next direction and remaining distance instead of the entire route. This makes the algorithm useful without removing exploration from the game.

Data Structure Improvements

Before

  • Inventory stored in a list
  • No map-wide traversal
  • No validation that connections referenced real rooms
  • No deterministic tie-breaking for equal-distance targets

After

  • Inventory stored in a set to enforce uniqueness
  • BFS supports shortest-path and hint behavior
  • World validation checks connections, required items, reachability, and final encounter placement
  • Fixed north/east/south/west ordering makes equal-distance results predictable

Complexity and Trade-Offs

The breadth-first search runs in O(V + E) time because each reachable room and connection is processed no more than once. The current game map is small, so performance was not the main reason for the change. The stronger value was demonstrating an algorithmic solution that still scales naturally if more rooms and connections are added later.

I also chose a set for inventory because the important operations are uniqueness and membership rather than insertion order. A separate fixed item order preserves consistent display output, so the program gets the benefits of set operations without making the interface unpredictable.

Testing

The final algorithms artifact includes automated tests for world validation, shortest-path behavior, unreachable targets, equal-distance targets, current-room hints, final-battle hints, duplicate prevention, and compatibility with the earlier software design structure. The capstone verification recorded 14 of 14 tests passing.

Reflection

This enhancement changed how I viewed the original room dictionary. It was already a graph in practice, but treating it deliberately as one allowed the same data to support movement, validation, and search. The earlier software design enhancement made this easier because the map, player state, and command processing were already separated well enough to extend without rebuilding the program.

The most important design decision was how much information a hint should reveal. Returning an entire path would have been easier to demonstrate, but it would have weakened the exploration that the game is built around. Returning only the next move and distance created a better balance between algorithmic usefulness and player choice.
