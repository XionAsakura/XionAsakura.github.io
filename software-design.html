Enhancement One

Software Design & Engineering

For this category, I enhanced a Zelda-inspired Python text adventure originally created in IT 140. The goal was to keep the original story and gameplay while improving the internal design so the program would be easier to maintain, test, and expand.

Artifact Overview

The player controls Link, begins in Kokiri Forest, travels through connected rooms, collects six required items, and eventually reaches Ganon at the top of Hyrule Castle. The original version already supported navigation, inventory, item collection, win and loss conditions, exiting, and replay. I selected it because it is an early programming project that makes my growth in software design easy to see.

Why It Needed Improvement

Original Design

  • Game state stored in global variables
  • Main movement function handled many responsibilities
  • Commands were case-sensitive
  • Replay called main() recursively
  • Ganon was stored in the same field used for collectible items
  • Limited documentation and input handling

Enhanced Design

  • Player class owns location and inventory
  • Game class manages map, commands, events, movement, and session state
  • Input is normalized and supports shorter command formats
  • Replay uses one controlled outer loop
  • Ganon is represented as a dedicated encounter
  • Type hints, constants, docstrings, and clearer feedback were added

Key Engineering Decisions

Clear State Ownership

Moving the current room and inventory into a Player object made it easier to understand which data belongs to the player instead of allowing several functions to change shared global state.

Separation of Responsibilities

Command parsing, movement, item pickup, room events, final encounters, help, and exit confirmation were separated into focused methods. The program remains in one file, which is appropriate for its size, without keeping all behavior inside one large loop.

Controlled Input

Commands now tolerate capitalization differences and repeated spaces. The game also supports concise forms such as north and take Hammer while preserving the original command formats.

Reflection

The main lesson from this enhancement was that better software design does not have to change the visible experience. Most of the gameplay stayed familiar, but the code became easier to reason about because state and behavior were organized more carefully. I also had to avoid overengineering the project. Splitting a small text game into many files would have added structure without necessarily adding value, so I kept one organized file and used classes and focused methods as a practical middle ground.

This enhancement created the foundation for the later algorithms work. Once the map, player state, and command handling were more clearly separated, I could add graph traversal and a hint system without rewriting the entire game.
